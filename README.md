# AI 应用工程训练仓库

这是一个面向 AI 应用工程师实习能力的长期工程训练仓库。这里用小型、可验证的编码任务，持续训练 Python 工程、后端开发、LLM 应用、RAG、智能体、测试与生产工程能力。

目标是在 2027 年 1 月底具备 AI 应用开发实习所需的基本独立交付能力：能理解需求、做出设计取舍、实现和调试功能、审阅并解释测试、使用 Git 协作，并能评估 LLM 系统的质量、延迟与成本。每周默认投入 10–15 小时，主要展示成果是一套持续演进的“技术资料知识助手”。

## 学习方式

训练采用短反馈循环：

> 最少必要知识 → 编码任务 → 独立实现与手动验证 → 导师编写测试 → 测试与调试 → 代码审查与修改 → 最终审查 → 针对性提问 → 复盘

从 TASK-009 起，正式功能任务默认由学习者实现生产代码并完成基本手动验证，明确通知导师后，导师再编写测试。生产缺陷由学习者修复，测试缺陷由导师修正；以测试技术为主要学习目标的任务可以明确要求学习者亲自编写指定测试。既有任务不追溯应用新的分工。

每个正式任务原则上控制在 30 分钟到 3 小时有效编码时间，每周安排两个核心任务，最多一个可选任务。难度从 L1/L2 起步，根据审查和复盘证据提升；进入 L3 后，学习者先提交简短方案、取舍与失败分析，导师审查后再实现。

## 项目主线与里程碑

工程与 AI 功能交错推进，Python 和后端知识绑定同一项目：

> 服务与评测闭环 → 可引用的 RAG 基线 → 检索优化与单智能体 → 交付与实习展示

| 里程碑 | 建议窗口 | 主要成果 |
| --- | --- | --- |
| 服务与评测闭环 | 2026-10-05 至 2026-10-25 | 批量评测报告、分析结果存储与查询、数据库事务验证 |
| 可引用的 RAG 基线 | 2026-10-26 至 2026-11-22 | 公开技术资料的导入、维护、检索问答与来源定位 |
| 检索优化与单智能体 | 2026-11-23 至 2026-12-20 | 检索对照实验、受限的检索与原文读取工具、停止条件与预算 |
| 交付与实习展示 | 2026-12-21 至 2027-01-17 | Docker、离线 CI、基本访问控制、追踪与评测报告、演示材料 |
| 修复与缓冲 | 2027-01-18 至 2027-01-31 | 修复验收缺口、独立调试与小需求修改、模拟面试 |

日期用于安排容量，完成以验收证据为准；每周复盘可以调整节奏。已有任务代码、测试与复盘继续保留，从已验证能力逐步组织项目，保持既有分析接口行为。新接口在对应正式任务中定义。

项目初版处理 Markdown 和纯文本，沿用 Python、FastAPI、Pydantic 与 DeepSeek，采用 PostgreSQL、pgvector；先使用直接 SQL、精确向量检索和原生工具调用。Redis、SSE、多 Agent、MCP、高级框架与复杂解析作为可选扩展，具体技术只在服务于当前学习目标时引入。

提示词、模型配置、语料和评测样例都作为版本化工程资产。默认模型测试保持离线；本地集成测试使用隔离的测试数据库。真实 API 调用与评测必须显式开启，由学习者决定。检索质量与回答质量分别评估；全量测试通过不能替代真实模型效果评测，也不能单独证明实习能力达标。

导师协作规则见 [AGENTS.md](AGENTS.md)，阶段路线和验收成果见 [ROADMAP.md](ROADMAP.md)。

## Git 工作流程

- `develop` 是训练主分支。
- 本仓库由学习者个人使用，正式任务统一直接在 `develop` 开发，不为每个任务创建独立分支。
- 一个任务保持清晰的提交范围，提交信息使用 Conventional Commits 约定，例如 `feat: add document retrieval endpoint`、`test: cover document deletion rollback`。
- 代码审查时检查任务说明提交或上一任务完成提交到当前状态的完整差异，并同时检查未提交修改。
- 不自动推送、合并或提交，不改写已有历史；除非学习者明确要求对应操作。
- 不使用 `update`、`修改`、`fix bug` 等缺少信息的提交信息。

## 如何开始任务

1. 请求导师基于 [ROADMAP.md](ROADMAP.md)、最近的代码审查和每周复盘创建下一个任务。
2. 导师使用[任务模板](tasks/templates/task-template.md)给出学习目标、约束、验收标准和测试要求，但默认不提供完整实现。
3. 确认当前位于最新 `develop`，工作区状态明确，并记录本任务的审查基线。
4. L3 及以上任务先提交简短方案、取舍和失败分析，导师审查后再实现；L2 按明确合同实现。
5. 学习者独立实现生产代码并完成基本手动验证，记录实际命令、结果和已知问题；遇到困难时逐级请求提示，只有明确请求完整解答时才获取完整答案。
6. 明确通知导师“生产代码已完成，请开始编写测试”；导师依据任务合同和公开接口编写测试、fixture 与必要数据，默认不修改生产代码。
7. 运行测试，学习者审阅关键断言与 Mock 边界；测试有误由导师修正，生产实现有误由学习者修复，需求理解分歧先核对合同。
8. 记录验证结果并请求代码审查；测试专项任务按任务说明执行指定分工。完整流程见 [tasks/README.md](tasks/README.md)。

## 如何请求代码审查

提交代码审查请求时，说明任务编号、已运行的测试、已知问题和最不确定的设计决策。导师会基于任务基线到当前状态的完整差异，按以下维度反馈：

- 严重问题
- 主要问题
- 次要问题
- 缺失的测试
- 合理的设计
- 最终审查后的针对性问题

中间审查只围绕实际问题推动修复。代码通过最终审查后，导师再根据最终实现和修改过程提出 3–5 个针对性问题，确认学习者能解释设计原因、失败场景和测试策略。

学习者还需解释关键测试保护的行为、Mock 边界、可能的假阳性，以及某个生产缺陷为什么会使测试失败。每个里程碑安排一次综合审查，检查模块集成、完整差异与独立解释能力。

## 如何完成复盘

代码通过最终审查后，导师会提出 3–5 个针对性问题，并依据 diff、测试和审查记录起草“本次所学、关键错误及原因”等有证据支持的内容。学习者核对和补充这些内容，并独立回答针对性问题，双方使用[任务复盘模板](retrospectives/task-retrospective-template.md)共同定稿。L1/L2 使用 5–10 分钟简版，L3 以上使用完整版。任务复盘不记录下一步行动；任务与复盘完成后直接进入下一个任务。每周使用[每周复盘模板](weekly/weekly-review-template.md)，依据提交记录、已完成任务、测试和代码审查证据调整路线。
