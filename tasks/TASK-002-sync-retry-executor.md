# TASK-002 — 同步重试执行器

- **难度：** L2
- **预计有效编码时间：** 120–180 分钟
- **建议分支：** `learn/task-002-retry-executor`
- **状态：** 待确认

## 背景

LLM API、数据库和外部 HTTP 服务都可能出现暂时性失败，例如超时、连接中断或服务短暂不可用。工程代码通常不会对所有异常一律重试，而是需要明确：哪些错误可以重试、最多尝试几次、每次重试前等待多久、失败过程如何记录，以及最终失败时向调用者暴露什么信息。

本任务要求实现一个同步重试执行器。它接收一个无参数操作，根据重试策略执行该操作，并通过依赖注入使等待行为可以被快速、稳定地测试。本任务不连接真实外部服务，重点是重试语义、异常边界、类型设计、日志和测试。

## 学习目标

完成后，学习者应该能够：

- [ ] 使用 `Callable`、`TypeVar` 和明确的函数签名表达“接收操作并返回其结果”。
- [ ] 使用数据类建模重试策略，并验证配置是否合法。
- [ ] 区分可重试异常、不可重试异常和重试耗尽异常。
- [ ] 使用 `raise ... from ...` 保留最终失败的异常链。
- [ ] 使用标准库 `logging` 记录重试过程。
- [ ] 通过注入等待函数避免测试真实休眠，并用 pytest 验证调用次数和副作用。

## 前置知识

开始前需要理解以下核心概念：

- 函数也是对象，可以作为参数传递；`Callable[[], T]` 表示无参数并返回 `T` 的可调用对象。
- `TypeVar` 用于表达输入操作的返回类型与执行器返回类型保持一致。
- 异常类、异常实例、异常继承和 `except` 匹配规则。
- 数据类的 `__post_init__` 验证。
- `logging` 的 `WARNING` 与 `ERROR` 级别。
- pytest 的 `caplog`、参数化测试，以及标准库 `unittest.mock.Mock` 的基本用法。

建议先完成三个小实验：

1. 将一个无参数函数赋值给变量，再通过该变量调用函数并取得返回值。
2. 用 `isinstance(error, (TimeoutError, ConnectionError))` 观察异常元组的匹配行为。
3. 使用 `Mock(side_effect=[TimeoutError(), "ok"])` 观察连续调用的返回值、异常和 `call_count`。

## 功能要求

### 1. 项目位置

实现代码放在首次实现时创建的 `exercises/task_002_retry_executor/` 目录中。测试放在 `tests/test_task_002/`。保持结构最小，不修改 TASK-001 的实现。

### 2. 重试策略

使用数据类 `RetryPolicy` 表示策略，至少包含：

- `max_attempts: int`：最大尝试次数，包含第一次调用。
- `delay_seconds: float`：两次尝试之间的固定等待秒数。
- `retryable_exceptions: tuple[type[Exception], ...]`：允许重试的异常类型，默认包含 `TimeoutError` 和 `ConnectionError`。

创建策略时必须验证：

- `max_attempts` 必须是大于等于 1 的整数，布尔值不视为合法整数。
- `delay_seconds` 必须是大于等于 0 的整数或浮点数，布尔值不合法。
- `retryable_exceptions` 必须是非空元组，且每个元素都是 `Exception` 的异常类。
- 配置非法时抛出 `ValueError`，错误信息应指出具体字段和原因。

### 3. 重试耗尽异常

定义自定义异常 `RetryExhaustedError`，用于表示所有允许的尝试都因可重试异常失败。异常对象至少保存：

- `attempts`：实际尝试次数。
- `last_error`：最后一次捕获到的可重试异常。

异常文本应包含尝试次数和最后异常的类型或信息。

### 4. 执行入口

提供公开函数 `execute_with_retry`，它应：

- 接收一个无参数操作 `operation`，并返回该操作成功时的原始返回值。
- 接收 `RetryPolicy`。
- 支持注入等待函数；生产环境默认使用 `time.sleep`，测试中可以替换为不会真实等待的函数或 Mock。
- 使用模块级 logger 记录重试行为，不在生产代码中使用 `print`。
- 使用泛型类型标注，使执行器返回类型与 `operation` 返回类型一致。

### 5. 执行规则

- 第一次调用计为第 1 次尝试。
- 操作成功时立即返回，不再等待或重试。
- 捕获到策略允许的异常且仍有剩余次数时：记录一条 `WARNING` 日志，随后调用一次等待函数，再继续尝试。
- 每两次尝试之间恰好等待一次；即使 `delay_seconds` 为 0，也仍调用等待函数并传入 0。
- 捕获到策略允许的异常且次数已经耗尽时：记录一条 `ERROR` 日志，抛出 `RetryExhaustedError`，并使用异常链保留最后一次原始异常。
- 捕获到策略未允许的异常时：立即原样向外传播，不记录重试日志、不等待、不包装成 `RetryExhaustedError`。
- `max_attempts=1` 时仍必须执行一次操作；失败后不能等待或再次尝试。

### 6. 日志要求

- 每次准备重试前记录一条 `WARNING`。
- 重试耗尽时记录一条 `ERROR`。
- 日志应包含当前尝试次数、最大尝试次数以及异常类型或信息。
- 测试不要求匹配完整日志字符串，应通过日志级别和关键字段验证可观察行为。

## 约束

- 生产代码只使用 Python 标准库；测试可以使用 pytest。
- 不使用 tenacity、backoff 或其他第三方重试库。
- 不使用装饰器实现核心功能；装饰器会放到后续任务训练。
- 不实现异步重试、指数退避、随机抖动、超时控制或取消机制。
- 测试中禁止真实等待，不得直接调用会造成明显延迟的 `time.sleep`。
- 不连接真实网络、数据库或 LLM API。
- 所有公开函数、数据类字段和自定义异常保存的公开属性都必须具有明确类型。

## 验收标准

- [ ] 第一次成功时只执行一次操作，原样返回结果，不等待且不记录重试日志。
- [ ] 可重试异常发生后，如果后续尝试成功，返回最终结果，调用次数、等待次数和日志数量均正确。
- [ ] 可重试异常持续发生并耗尽次数时，抛出 `RetryExhaustedError`，其属性和异常链均正确。
- [ ] 不可重试异常第一次出现时立即原样传播，不等待、不重试、不包装。
- [ ] `max_attempts=1` 的成功和失败行为均符合规则。
- [ ] 非法策略在创建时抛出信息明确的 `ValueError`。
- [ ] 执行器支持返回字符串、字典或其他类型，而不改变返回值。
- [ ] 在仓库根目录执行 `python -m pytest -q` 时全部测试通过。

## 测试要求

至少覆盖以下测试：

- [ ] 第一次调用成功。
- [ ] 前两次抛出可重试异常、第三次成功。
- [ ] 所有尝试均失败并耗尽次数。
- [ ] 不可重试异常立即传播。
- [ ] `max_attempts=1`。
- [ ] `delay_seconds=0` 时等待函数仍被正确调用。
- [ ] `RetryExhaustedError.attempts`、`last_error` 和 `__cause__`。
- [ ] `WARNING`、`ERROR` 日志的数量、级别和关键信息。
- [ ] `RetryPolicy` 各字段的非法值，优先使用参数化测试。
- [ ] 操作返回可变对象时，执行器返回的是同一个对象，而不是复制品。

测试应明确断言操作调用次数和等待函数调用次数，避免通过真实时间判断是否发生等待。

## 边界情况

- 可重试异常的子类。
- 不同尝试抛出不同的可重试异常，最终异常应保留最后一次失败。
- 操作成功前已经修改了外部状态；执行器不能自动回滚操作副作用，应由调用者负责幂等性。
- logger 没有配置 handler 时，执行逻辑仍应正常工作。
