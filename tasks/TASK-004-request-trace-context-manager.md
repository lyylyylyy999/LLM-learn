# TASK-004 — 请求追踪上下文管理器

- **难度：** L2
- **预计有效编码时间：** 120–180 分钟
- **开发分支：** `develop`
- **状态：** 待确认

## 背景

调用 LLM、数据库或外部 HTTP 服务时，工程系统通常需要记录一次请求是否成功、耗时多久以及失败类型。把开始计时、结束计时和异常记录散落在每个 `try/finally` 中容易重复，也容易漏掉失败路径。

本任务要求实现一个同步请求追踪上下文管理器。它不调用真实外部服务，而是围绕 `with` 代码块收集结构化结果，并通过注入时钟和结果接收函数使生命周期行为可以稳定测试。重点是理解上下文管理器协议、异常传播和资源清理式控制流。

## 学习目标

完成后，学习者应该能够：

- [ ] 解释 `with` 如何调用 `__enter__` 和 `__exit__`。
- [ ] 根据 `__exit__` 的异常参数区分成功与失败路径。
- [ ] 理解 `__exit__` 返回值如何决定异常是否被抑制。
- [ ] 使用数据类表示结构化追踪结果。
- [ ] 通过依赖注入测试时间和结果提交行为，不依赖真实时间。

## 前置知识

- 上下文管理器协议及 `with ... as ...` 的基本执行顺序。
- `__exit__(exc_type, exc_value, traceback)` 三个异常参数的含义。
- `time.perf_counter` 适合测量持续时间，而不是表示日历时间。
- `Callable`、联合类型和 `Literal` 的基本类型标注。
- Mock 的 `side_effect`、`call_count`、`call_args` 和对象身份断言。

建议先完成三个最小实验：

1. 编写只打印进入、退出顺序的上下文管理器，分别运行正常代码块和抛出异常的代码块。
2. 改变 `__exit__` 的返回值，观察异常是否继续传播。
3. 使用 `Mock(side_effect=[10.0, 10.25])` 模拟两次时钟调用并计算差值。

## 功能要求

### 1. 项目位置

实现代码放在首次实现时创建的 `exercises/task_004_request_trace/` 目录中，测试放在 `tests/test_task_004/`。

保持模块结构最小，不修改 TASK-001、TASK-002 和 TASK-003 的已有实现。

### 2. 追踪结果模型

使用数据类 `TraceRecord` 表示一次完成的追踪，至少包含：

- `request_name: str`：请求或操作名称。
- `status`：只能表示成功或失败两种状态。
- `elapsed_seconds: float`：代码块执行耗时。
- `error_type: str | None`：成功时为 `None`，失败时为异常类名。

字段必须具有明确类型。追踪结果创建后不应再被修改。

### 3. 上下文管理器

实现类 `RequestTrace`，它应：

- 接收非空白的 `request_name`，非法时抛出包含字段原因的 `ValueError`。
- 接收无参数时钟函数，默认使用 `time.perf_counter`。
- 接收结果接收函数 `sink`；一次追踪结束后，将一个 `TraceRecord` 传给它。
- 在 `__enter__` 中记录开始时间并返回当前管理器对象。
- 在 `__exit__` 中记录结束时间、计算耗时、创建追踪结果并恰好调用一次 `sink`。
- 将最终记录保存在公开只读语义的 `record: TraceRecord | None` 属性中；进入前为 `None`，退出后为最终结果。
- 不抑制 `with` 代码块抛出的异常，也不把它转换成新异常。
- 公开接口和属性具有明确类型标注。

### 4. 成功与失败语义

- 正常离开代码块时，记录成功状态，`error_type` 为 `None`。
- 代码块抛出异常时，记录失败状态，`error_type` 为实际异常类名。
- 失败记录提交给 `sink` 后，原异常对象必须继续向外传播。
- 无论成功还是失败，时钟都应恰好调用两次，`sink` 都应恰好调用一次。
- 耗时等于结束时刻减去开始时刻；测试浮点数时使用合适的近似比较。

### 5. 生命周期限制

- 一个 `RequestTrace` 实例只能进入一次。
- 同一实例重复进入或嵌套进入时，抛出 `RuntimeError`，且不得产生第二条记录。
- 不同实例之间状态相互独立。

## 约束

- 生产代码只使用 Python 标准库；测试可以使用 pytest。
- 必须自行实现类形式的 `__enter__` 和 `__exit__`，不使用 `contextlib.contextmanager`。
- 不实现异步上下文管理器。
- 不调用真实 LLM、网络或数据库。
- 测试不依赖真实时间，也不使用 `sleep` 判断耗时。
- 不在模块导入时配置根 logger、创建追踪记录或产生输出。
- 不捕获 `BaseException`，也不根据异常类型选择性抑制异常。
- `sink` 自身抛出异常时的恢复策略不属于本任务范围，可以让它自然传播。

## 验收标准

- [ ] 正常代码块生成一条字段正确的成功记录。
- [ ] 异常代码块生成一条失败记录，并继续抛出同一个原异常对象。
- [ ] `with ... as ...` 返回当前 `RequestTrace` 实例。
- [ ] 进入代码块之前和执行期间不会提前调用 `sink`。
- [ ] 时钟调用次数、结果接收次数和调用参数正确。
- [ ] 重复或嵌套使用同一实例会被拒绝，且不会覆盖第一条记录。
- [ ] 两个独立实例不会共享开始时间或最终记录。
- [ ] 非法 `request_name` 在创建实例时被拒绝。
- [ ] 在仓库根目录执行 `python -m pytest -q` 时全部测试通过。

## 测试要求

至少覆盖以下测试：

- [ ] 正常退出：状态、名称、耗时和 `error_type`。
- [ ] 异常退出：异常对象身份、失败记录及异常类名。
- [ ] `__enter__` 返回对象身份。
- [ ] 代码块执行期间 `record is None`，且 `sink` 尚未调用。
- [ ] 时钟恰好调用两次，`sink` 恰好调用一次且收到同一个记录对象。
- [ ] 空字符串和仅含空白的 `request_name`，优先使用参数化测试。
- [ ] 同一实例顺序使用两次。
- [ ] 同一实例嵌套使用。
- [ ] 两个实例的状态相互独立。

测试应围绕公开行为断言，不直接依赖私有字段名或复制实现逻辑。

## 边界情况

- 代码块立即正常退出。
- 代码块立即抛出异常。
- 时钟返回相同数值，耗时为 `0.0`。
- 异常没有消息，但仍能记录异常类名。
- `sink` 保存收到的记录供调用者后续汇总。
