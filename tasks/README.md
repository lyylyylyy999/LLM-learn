# 正式任务

本目录保存正式编码任务。每个任务使用 `TASK-XXX-short-description.md` 命名，并从[任务模板](templates/task-template.md)创建。

## 任务生命周期

1. **待确认**：导师根据路线图和最近证据提出任务、难度及预计时间。
2. **进行中**：学习者确认当前位于 `develop`、工作区状态明确，记录任务说明提交或上一任务完成提交为审查基线。L3 及以上任务先提交简短方案、取舍和失败分析，导师审查后再独立实现。
3. **手动验证与导师测试**：从 TASK-009 起，学习者完成生产代码和基本手动验证，记录命令与结果，明确通知导师开始编写测试。导师根据任务合同和公开接口编写测试、fixture 与必要数据，默认不修改生产代码。
4. **代码审查与修改**：运行测试并区分生产缺陷、测试缺陷和需求分歧。生产缺陷由学习者修复，测试缺陷由导师修正，需求分歧先核对合同；审查与修改可以重复多轮。审查检查基线到当前 `HEAD` 的完整差异及未提交修改。
5. **最终审查**：代码满足验收标准后，导师根据最终实现提出 3–5 个针对性问题。
6. **已完成**：导师基于审查证据起草本次所学和关键错误，学习者核对补充并回答针对性问题；双方共同完成对应难度的复盘，满足任务完成定义，并获得建议提交信息。

一个任务聚焦一个主要学习目标，预计有效编码时间通常为 30 分钟到 3 小时。复杂功能应拆分，不在任务进行中悄悄扩大范围。

目录中的任务文件记录稳定需求和验收条件；实现代码放在相应的 `exercises/` 或 `projects/` 子目录中，这些目录在首次需要时再创建。

## 设计责任与任务节奏

- 正式任务根据 [ROADMAP.md](../ROADMAP.md)、最近审查、知识缺口、项目上下文和每周复盘逐项设计，不提前一次生成全部任务。
- 每周安排两个核心任务，最多一个可选任务；根据实际投入与验收结果调整，不以任务数量判断能力。
- L2 给出明确的功能合同、约束和可观察的验收标准；L3 及以上要求学习者先解释方案、关键取舍和失败路径。导师继续使用正式任务模板与渐进式提示，默认不提供完整生产实现。
- 已稳定掌握的异常映射、配置与校验作为后续质量要求，减少没有新学习证据的重复任务。
- 每个里程碑安排综合审查，检查模块集成、完整差异与独立解释能力；里程碑验收不能替代单个任务的完成定义。

## 测试协作与完成证据

TASK-001 至 TASK-008 保持原流程。从 TASK-009 起，正式功能任务默认由学习者实现生产代码、导师编写测试；以 pytest、异步测试、HTTP 或数据库事务测试等新测试技术为主要学习目标时，可以要求学习者亲自编写任务指定的测试。

- 学习者在通知导师前完成基本手动验证，说明已知问题和最不确定的设计决策；导师不提前代写生产实现。
- 测试从外部可观察行为出发，覆盖正常路径、核心失败与安全或数据一致性边界。敏感标记、失败输入和 Mock 必须真实进入目标执行路径，避免错误实现仍然通过。
- 导师不降低任务合同以迁就实现；生产缺陷继续用渐进式提示推动学习者修复，测试自身有误时由导师修正。
- 默认模型测试保持离线；本地集成测试使用隔离的本地测试数据库，环境与命令在任务中明确。真实 API、付费服务及其他外部副作用测试必须由学习者显式开启。
- 学习者审阅测试，能够解释关键断言、Mock 边界、可能的假阳性和生产缺陷触发测试失败的机制。
- 记录实际运行的验证命令与结果，保留 pytest、Ruff、mypy 和 `git diff --check` 检查；模型与检索评测另行保存运行条件、报告与失败案例。
- 审查至少包含严重问题、主要问题、次要问题、缺失的测试和合理的设计；没有发现时明确写“无”。最终审查通过后，导师提出 3–5 个针对性问题。
- 学习者准确回答最终审查问题，与导师按难度共同完成复盘，并获得建议提交信息后，任务才可标记为已完成；提交与推送由学习者决定。
