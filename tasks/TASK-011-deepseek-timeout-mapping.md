# TASK-011 — DeepSeek 调用超时与安全 HTTP 映射

- **难度：** L2

- **开发分支：** `develop`

## 背景

TASK-010 已能从环境变量创建 DeepSeek 客户端并启动分析服务，但客户端仍使用 SDK 的隐式超时和自动重试默认值。模型服务无响应时，请求可能等待很久；即使 SDK 最终抛出超时异常，当前领域层和 HTTP 层也没有把它识别为独立失败类型。

本任务只处理“上游调用超时”这一条可靠性路径：为客户端设置明确的超时边界，将 SDK 超时转换为领域异常，再映射为安全、稳定的 HTTP `504 Gateway Timeout`。连接失败、限流和业务重试暂不加入，避免一次任务承担过多概念。

## 功能要求

### 1. 显式客户端超时配置

- 在 TASK-010 的应用工厂中读取可选环境变量 `DEEPSEEK_TIMEOUT_SECONDS`。
- 未配置时默认使用 `30.0` 秒。
- 配置值必须能够解析为浮点数，并且是有限的正数；空字符串、非数字、`0`、负数、`NaN` 和正负无穷均视为无效配置。
- 无效值必须在应用创建阶段产生明确的配置错误；错误和 traceback 不得回显原始配置值，也不得创建客户端。
- 将验证后的秒数通过客户端的 `timeout` 参数传入。
- 创建客户端时显式设置 `max_retries=0`。本任务保持一次业务调用只触发一次 SDK 请求尝试，不实现新的重试策略。
- 模块导入和应用创建仍不得发送模型请求。

### 2. SDK 超时转换为领域异常

- 在 TASK-007 的结构化分析模块中新增公开异常 `LLMTimeoutError`，并让它继承 `LLMError`。
- `structured_analysis()` 只在 SDK 请求调用边界捕获 `openai.APITimeoutError`，并转换为 `LLMTimeoutError`。
- `LLMTimeoutError` 的消息不得包含 API Key、完整对话、SDK 原异常文本或其他上游响应内容。
- 保留原异常作为异常原因，供内部调试使用；不得把异常原因序列化到 HTTP 响应。
- 不要把 `Exception`、`openai.OpenAIError` 或其他宽泛异常全部包装成超时。未知编程错误必须保持可见，避免被误报为上游超时。
- 原有正常响应、未完成响应和结构化输出校验失败行为保持兼容。

### 3. HTTP 超时响应

- TASK-009 的 `POST /analyses` 收到 `LLMTimeoutError` 时返回 `504 Gateway Timeout`。
- 响应沿用现有错误结构：

```json
{
  "detail": {
    "code": "llm_timeout",
    "message": "非空且不包含上游异常细节的通用提示"
  }
}
```

- `LLMTimeoutError` 必须在更宽泛的 `LLMError` 之前处理，否则超时会被错误映射为现有 `502 llm_response_error`。
- 原有 `LLMError`、`StructuredOutputError`、请求校验和成功响应合同保持不变。
- HTTP 响应和应用日志不得包含 API Key、对话内容或 SDK 原异常文本。

### 4. 运行说明

- 更新 TASK-010 旁的运行说明，补充 `DEEPSEEK_TIMEOUT_SECONDS` 的用途、默认值和合法范围。
- 说明当前客户端禁用 SDK 自动重试，因此一次 `POST /analyses` 最多发起一次 SDK 请求尝试。
- 不要求通过真实 DeepSeek 请求制造超时；真实 API 调用仍由学习者显式决定。

## 边界情况

- `DEEPSEEK_TIMEOUT_SECONDS` 缺失、空字符串、带前后空白的合法数字和普通非数字。
- `0`、负数、`NaN`、`inf` 和 `-inf`。
- SDK 在生成任何响应对象之前超时，此时没有响应 ID 或 token 用量可供记录。
- `LLMTimeoutError` 同时也是 `LLMError`，异常处理顺序错误会把 `504` 降级为 `502`。
- 应用创建成功但从未收到请求；此时不得调用模型。
- Pydantic 在路由调用前拒绝非法请求；此时不得触发超时替身。
