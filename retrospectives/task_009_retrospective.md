## 本次所学（共同确认）

- FastAPI 在调用路由前验证 Pydantic 请求模型；缺失字段、错误类型、纯空白和额外字段返回 `422`，分析器不会被调用。
- 应用工厂接收可替换的同步分析器。离线测试能够验证 HTTP 状态、响应内容、调用次数和传入参数，但不能证明真实 SDK、网络或模型行为。
- 已知模型失败可以映射为带稳定 `code` 和通用 `message` 的 `502` 响应，并避免泄露原异常信息。当前分析器是同步网络调用；若在 `async def` 路由中直接执行它，等待网络时会阻塞事件循环。

## 关键错误（共同确认）

- **错误：**首次实现的两种 `502` 响应只返回错误码字符串，缺少任务合同要求的通用 `message`；对应测试失败后补齐了两个字段。
  **原因（代码层面）：**初版将 `detail` 设为字符串，因而响应中没有独立的 `message` 字段。
- **错误：**为在浏览器地址栏测试而新增的 GET 路由会把对话放进 URL，且每次访问都触发模型调用；增量审查后已移除。
  **原因（代码层面）：**把需要执行分析的操作放在 GET 请求中，并用查询参数传递对话，没有保持原有 POST 请求体的边界。

## 最终审查问题（学习者回答）

### 1. 为什么非法请求返回 `422` 时，分析器一次也不应被调用？

**回答：**请求模型验证发生在路由调用之前；非法请求不会进入调用分析器的路由逻辑。

### 2. `RecordingAnalyzer` 能证明什么，不能证明什么？

**回答：**它能证明 HTTP 层调用分析器的次数和传入内容，也能提供可控响应供接口测试；因为响应是手动模拟的，不能证明真实 SDK、网络或模型调用的行为。

### 3. 为什么使用同步 `def` 路由？直接改成 `async def` 有什么风险？

**学习者回答：**异步路由可能在等待期间阻塞事件循环。

**导师澄清：**风险来自在 `async def` 路由中直接调用当前同步分析器：网络等待会阻塞事件循环；普通 `def` 路由由 FastAPI 在线程池中执行。

### 4. 为什么 `502` 保留错误码，却不返回原异常文本？

**学习者回答：**返回原异常文本可能泄露敏感信息。

**导师补充：**稳定错误码供客户端识别失败类型；原异常文本可能包含密钥、对话或模型输出。
