## 本次所学（共同完成）

- JSONL 的每一行是包含 JSON 文本的字符串。Pydantic 的 `model_validate()` 校验已经解析成 Python 对象的数据；直接校验 JSON 字符串应使用 `model_validate_json()`，或先用 `json.loads()` 解析。
- 结果文件中的显式 `null` 表示该样例本次没有有效结果，应计入批量报告的失败样例；结果文件完全缺少某个 `case_id` 表示两侧输入不一致，应拒绝整次运行。
- 输入文件的 SHA-256 只能标识参与运行的原始文件字节。输入未变而评分代码发生变化时，哈希不变，因此必须单独记录并更新人为声明的 `scorer_version`。
- 在创建报告文件前完成校验、评分和 JSON 序列化，可以保证这些阶段失败时不留下目标文件。使用 `"x"` 模式可以拒绝覆盖已有报告；创建成功后若写入中途失败，仍可能留下不完整文件，这是当前实现的已知边界。

## 关键错误与根因（共同完成）

- **错误：**初版使用 `OutcomeMessage.model_validate(line)` 处理 JSONL 字符串，导致合法的非空结果文件在第一行就被拒绝。
  **根因：**没有区分“JSON 文本”和“已解析的 Python 对象”对应的 Pydantic 校验入口。
  **如何避免再次发生：**先明确接口接收的数据层级，并用一个最小合法样例验证正常路径，再补错误输入。
- **错误：**初版没有拒绝空白 `scorer_version`，且结果 `case_id` 只使用普通 `str`。
  **根因：**实现时关注了文件解析与报告写入主路径，没有逐项核对任务中的非空约束。
  **如何避免再次发生：**实现前把输入合同拆为文件级、行级和字段级检查清单，并用边界测试逐项验证。
- **测试风险：**最初的重复 ID 用例只断言抛出宽泛异常，错误实现可能在解析第一行时失败，使测试产生假阳性。
  **根因：**断言只验证“失败”，没有验证失败发生在目标执行路径和正确分类。
  **如何避免再次发生：**为关键失败断言行号或错误类别，并让敏感标记和重复数据真实到达目标分支。

- 可复现报告至少要保存输入身份和评分规则身份；二者解决不同问题，不能相互替代。

## 最终审查问题（学习者回答）

### 1. 为什么 `model_validate(line)` 会拒绝有效 JSONL 行，而修正后的解析方式可以接收？

**学习者回答：**`line` 是字符串，不能作为已经解析的对象交给 `model_validate()`；修正后使用面向 JSON 文本的校验方式。

### 2. 显式 `null` 与完全缺少某个 `case_id` 分别表示什么？

**学习者回答：**显式 `null` 是允许的输入，表示本次没有有效结果；完全缺少某个 ID 属于输入不一致，会抛出异常。

### 3. 输入哈希能证明什么？为什么还需要 `scorer_version`？

**学习者回答：**哈希不能表示运行次数，只能识别输入内容。评分代码改变而输入文件不变时，输入哈希不会改变，因此应更新 `scorer_version` 来标识新的评分规则。

### 4. 为什么在创建报告前完成评分和序列化？写入中途失败时有什么边界？

**学习者回答：**创建文件前失败时不会产生目标文件；创建后写入中途失败，可能留下不完整、不可用的文件。
