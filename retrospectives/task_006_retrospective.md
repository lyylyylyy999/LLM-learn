## 本次所学（共同确认）

- 理解了依赖注入对可测试性的价值：通过注入模型客户端和单调时钟，可以在不访问真实 API 的情况下验证请求参数、结果映射、异常传播和耗时；`time.perf_counter()` 不受系统墙上时钟调整影响，更适合测量持续时间。
- 理解了默认离线测试与真实冒烟测试的职责边界：Mock 测试用于快速、确定且无费用地覆盖业务分支，真实测试则用于验证 SDK、DeepSeek `base_url`、认证、模型名以及实际响应结构能够协同工作。
- 学会了把稳定规则放入 `instructions`，把待处理的外部对话数据放入 `input`，并通过显式环境变量、脱敏日志和最小依赖清单控制配置、安全性与可复现性。

- **错误：**实现和测试曾多次与任务合同发生偏差，包括模型环境变量名不一致、提示词要求不存在的结构化输出、成功路径使用错误日志级别，以及真实冒烟记录没有及时随最终实现更新。
  **原因：**修改局部行为后没有同步检查任务文档、生产代码、测试和运行证据这四层合同，导致各部分分别正确但组合后不一致。
- **错误：**部分安全性测试最初只断言敏感内容“不存在”，却没有证明目标日志实际产生；空输入测试也检查了错误的 Mock 层级，依赖清单一度依赖传递依赖而非声明直接使用的包。
  **原因：**测试最初只考虑正确实现下能否通过，没有反向验证错误实现是否也会通过，因此出现假阳性和可复现性缺口。

## 最终审查问题（学习者回答，导师确认）

### 1. 为什么注入客户端和单调时钟？

**回答：**依赖注入更方便测试，可以替换真实客户端和时钟。测量耗时不使用 `time.time()`，是因为系统时钟发生调整时可能导致持续时间计算错误；单调时钟不会倒退。

### 2. 为什么 SDK 异常保持原样传播？

**回答：**如果统一包装成 `LLMError`，上层就不知道原来的异常是什么。保留 SDK 原异常及 traceback 后，上层可以区分认证、限流、网络连接等失败，并决定是否重试、降级或提示用户；业务层识别出的非完成响应则可以使用 `LLMError` 表达统一的业务语义。

### 3. 为什么默认测试不能调用真实模型，又必须保留真实冒烟测试？

**回答：**每次测试都调用真实模型会产生不必要的费用并增加时间成本，而且外部服务存在不确定性。默认测试应使用 Mock，但仍需要至少一次真实测试，验证 SDK、配置和真实服务之间的集成确实可用。

### 4. 为什么要分离 `instructions` 和 `input`？

**回答：**`instructions` 负责稳定规则，`input` 负责本次问题或待处理对话。分开后更便于维护，也能明确区分应用规则与外部数据，减少把用户内容误当成系统规则的风险。

### 5. 为什么日志测试既要检查不泄密，也要检查日志存在？

**回答：**因为日志完全不存在时同样不会包含敏感数据；如果只检查“不包含”，即使生产代码删除了日志，测试也会错误通过。必须先证明预期日志确实产生，再验证其中没有敏感内容。
