## 本次所学（共同确认）

- 配置校验应发生在模块导入之后、应用创建期间。模块导入不读取密钥、不创建客户端；应用工厂发现配置无效时拒绝创建应用，避免错误延迟到第一条请求才暴露。
- 离线模拟测试、本地服务启动检查和真实模型请求提供不同范围的证据：模拟测试验证可控输入和响应下的程序行为；访问 `/openapi.json` 验证服务能够启动且路由文档可访问；真实请求验证当次 SDK、网络、模型和响应解析链路。一次真实请求成功仍不能证明模型回答始终正确或服务长期稳定。
- 创建 DeepSeek 客户端不会发送模型请求或消耗模型额度。错误处理既要提供明确的配置错误，也要避免原始配置值通过异常链、日志或响应泄露；`raise ... from None` 可以抑制原异常在 traceback 中的展示。

## 关键错误（共同确认）

- **错误：**初版配置校验发生得过晚，无效配置仍可能创建应用，直到收到请求才暴露错误。
  **原因：**没有准确区分模块导入、应用创建和请求处理三个生命周期阶段分别应承担的职责。
- **错误：**将 `DEEPSEEK_MAX_OUTPUT_TOKENS` 转换为整数失败时保留了原异常链，恶意或误填的敏感内容可能出现在 traceback 中。
  **原因：**初次修复只统一了面向调用方的错误信息，没有同时检查底层异常链是否仍会展示原始输入。

## 最终审查问题（学习者回答）

### 1. 为什么 API Key 必须在应用创建时校验，而不是模块导入时或首个请求时？

**学习者回答：**配置校验是在模块导入之后、请求之前应该处理的事情；如果校验不通过，不允许创建应用。

**导师补充：**这样既能保持模块导入无副作用，也能让部署和启动阶段尽早发现错误，避免无效应用开始接收请求。

### 2. `raise ValueError(...) from None` 隐藏了什么？为什么仍需保留清晰的配置错误？

**学习者回答：**它使 traceback 不再展示原异常信息，避免泄露配置中设置的内容。

**导师补充：**`from None` 抑制的是原异常在 traceback 中的显示，不等于删除原异常，也不能替代对日志和 HTTP 响应的脱敏检查；新的配置错误仍要指出哪个配置无效以及合法范围，但不能回显原始值。

### 3. 离线模拟测试、本地 `/openapi.json` 检查和真实模型请求分别能验证什么？

**学习者回答：**离线模拟测试验证模拟响应下的功能，不能证明真实模型行为；本地 `/openapi.json` 检查验证路由文档可访问，不能证明模型调用链路；真实模型请求验证真实 API 链路和当次响应，但不能证明大量重复调用时仍然稳定。

**导师补充：**一次真实请求也不能证明模型回答始终正确，因为模型输出具有不确定性，仍需要本地结构校验、评测集和持续回归验证。

### 4. 创建客户端与实际发送模型请求在成本和验证范围上有什么区别？

**学习者回答：**创建客户端的成本更低，不消耗模型 API 额度，也不能验证模型响应；实际发送请求会产生额度或费用，能够验证当次响应内容。

**导师补充：**客户端构造还可以验证配置读取、SDK 参数传递和应用装配；真实请求进一步验证密钥、网络、上游 API 和响应解析，但一次成功不能代表长期可靠性。
